## 1. 结论

### 1.1 设计一致性

**结论：通过。**

代码实现设计覆盖了架构文档中的全部核心构件和关键运行流程，没有发现与以下原则相冲突的设计：

- 一个连续的个人助理身份。
- 事件驱动，而不是聊天窗口驱动。
- Router/Worker 分层。
- 控制面与执行面分离。
- 低风险静默执行。
- 高风险飞书审批。
- 审批绑定具体动作。
- 执行后独立验证。
- 本地优先和最小权限。
- 计算、状态、执行环境分离。
- 独立 Watchdog。

**结论：尚未检查。**

当前仓库只有架构和实现设计文档，没有可运行代码、迁移或测试。因此本报告只能证明“实现设计没有违背架构”，不能证明“代码已经符合架构”。代码落地后需要重新执行本文第 6 节的实现验收。

## 2. 逐项一致性矩阵

状态说明：

- **设计覆盖**：实现设计有明确机制。
- **设计扩展**：为满足架构目标而增加的必要工程机制，不改变原架构。
- **待实现验证**：需要代码、测试或外部平台配置才能确认。
- **未覆盖**：实现设计没有对应机制。

## 3. 关键架构约束的代码化检查

### 3.1 控制面不能被执行面篡改

设计符合。

- Worker 的写工具只调用 `ActionGateway.propose()`。
- `authorize()`、租约签发和飞书回调只位于控制面。
- Worker 没有 SQLite 文件和数据库凭据，只能调用受限内部 API。
- 只有 `assistant-app` 可以写 SQLite。
- 连接器 `execute()` 要求合法 `ValidatedExecutionLease`。

实现时必须额外检查：

- `assistant-app` 是唯一持有 SQLite 写连接的进程。
- Worker 内部 API 具有短期 Token 和任务作用域。
- Codex 工作区不挂载 SQLite、Vault 或其他任务目录。
- 连接器写入方法不能暴露为 Agent 可直接调用的通用 HTTP 工具。

### 3.2 审批绑定具体动作

设计符合，并强化了原架构。

原架构要求审批绑定 `actionDigest`。实现设计进一步规定：

- 正文、文件、草稿等引用在审批前冻结为不可变快照或内容 Hash。
- 摘要覆盖连接器版本、目标、参数、副作用和过期时间。
- 回调必须校验审批人、摘要、状态和事件 ID。
- 修改内容采用新动作、新摘要、新审批，不能复用旧批准。

这解决了“审批的是摘要，但执行时引用的草稿已经变化”的漏洞。

### 3.3 静默执行与结果验证

设计符合。

- 静默只表示“不打断用户审批”，不表示“没有记录”。
- 自动动作仍要有策略版本、租约、回执、验证和审计。
- 验证由独立 Job 完成，不能只采用 Codex 或 Worker 自报成功。
- 验证结果会回传 Codex 线程做最终验收检查，但控制面仍保留最终状态权。

### 3.4 长任务、设备离线和审批等待

设计符合。

- 任务状态在 SQLite，不绑定某个进程或 Codex Thread。
- 等待审批时不保持模型循环，不消耗 Token。
- 设备任务保留到设备上线，控制面不假定设备始终在线。
- Device Daemon 只领取具体动作，不持有全局会话。
- Codex Thread 丢失后可以从 SQLite 任务状态和任务工作区重建。

### 3.5 一个 Agent 与多个 Worker

设计符合。

- 用户维度的 Assistant/时间线是产品实体。
- Task、Codex Run 和 Codex Thread 是内部执行实体。
- 控制面维护全局记忆和进行中任务，Codex Worker 只获得当前任务的最小上下文。
- 这不要求底层只能存在一个 Codex 线程，符合架构中“逻辑上只有一个 Agent”的表述。

## 4. 实现设计对原架构的必要扩展

以下扩展不改变原架构目标，但代码实现需要它们：

| 扩展 | 原因 |
| --- | --- |
| `outcome_unknown` 动作状态 | 第三方动作可能成功但本地丢失回执，原状态机没有明确表达 |
| `jobs` 持久任务表 | 让事件、审批、执行和验证可在进程重启后恢复 |
| `thread_subscriptions` | 让同一 Issue/邮件线程的后续事件直接关联任务，减少重复 Router 成本 |
| 不可变参数快照 | 防止引用对象在审批后变化 |
| 设备签名命令协议 | 落实“执行环境留在设备、控制面不持有长期凭据” |
| SQLite 单写者 | 避免 Worker、Daemon 和控制面互相争抢写锁 |
| `codex_thread_id` 持久化 | 在保持任务连续性的同时不把 Codex Thread 当成事实源 |
| `cancel_requested` 用户事件 | 支持执行中用户停止任务 |

## 5. 尚未闭合的产品与平台事项

这些问题来自原架构的待确认项，不构成设计矛盾，但会影响上线：

1. 首期具体接入哪些应用，以及是否支持仅本地保留原始正文。
2. 飞书审批人身份映射和委托审批规则。
3. 低风险自动写入白名单的首版范围。
4. 个人数据保留期限、删除策略和导出格式。
5. Device Daemon 支持的桌面系统和签名发布流程。
6. Codex SDK/CLI 版本、默认模型、鉴权方式、预算上限和隐私条款。
7. 对不可逆动作的补偿能力和用户提示方式。
8. 用户是否允许夜间主动执行以及提醒频率。

建议在 Sprint 1 开始前确定第 1、2、3 项，其余可以随实现迭代关闭。

## 6. 代码落地后的补检项

当代码进入仓库后，应按以下方式重新检查，而不是重新阅读文档：

### 6.1 静态检查

- 检查依赖图，确认 `domain` 不依赖 Fastify、数据库、模型 SDK 和飞书 SDK。
- 检查 Worker 模块没有导出 `authorizeAction`、租约签发、SQLite 写入或飞书回调处理。
- 检查只有控制面创建 SQLite 写连接。
- 检查外部输入均经过 Schema。
- 检查所有写工具都必须传入动作 ID 和租约。

### 6.2 数据库检查

- 验证 `(user_id, idempotency_key)` 唯一约束。
- 验证 `execution_leases(action_id)` 唯一约束。
- 验证外键、`STRICT` 表、JSON 字段和 `user_version` 迁移。
- 验证 `BEGIN IMMEDIATE` Job 领取不会重复派发。
- 验证 SQLite busy/locked 次数和写事务耗时。
- 验证审批、租约和执行 Job 在单个短事务内提交。

### 6.3 运行测试

- 重放同一 Webhook 100 次，只产生一个有效事件和一个任务。
- 并发点击飞书批准两次，只执行一次。
- 执行中杀死 Worker，验证不会无审计地重复写第三方。
- 关闭设备后重启控制面，任务仍存在。
- 审批等待 24 小时后重启系统，旧审批不能执行。
- 修改草稿正文后重新提交，必须生成新摘要和新审批。
- Worker 和控制面重启后能够恢复 Job、任务和 Codex Thread。

### 6.4 安全检查

- 在所有日志、Trace、Prompt 和数据库非敏感列中扫描凭据。
- 用恶意应用内容测试 Prompt Injection。
- 尝试让 Worker 调用未声明 connector capability。
- 尝试用伪造飞书回调和错误审批人批准动作。
- 尝试让 Device Daemon 执行未注册命令或任意 Shell。
- 尝试让 Codex 读取 SQLite、Vault、用户 Home 或其他任务工作区。
- 尝试通过恶意应用内容诱导 Codex 直接执行外部写操作。

### 6.5 Codex 集成检查

- 固定并记录 Codex SDK、CLI 和默认模型版本。
- 仅在 Codex 健康检查通过后启动任务领取。
- 使用 `workspace-write`，禁止 `danger-full-access` 和绕过沙箱的参数。
- Codex 最终输出必须通过严格 Zod Schema。
- `codex_thread_id` 每次 Run 都持久化。
- Thread 恢复失败时，能从任务工作区重新构建上下文。
- 数据请求、修复计划和 Codex 总步数均设有上限。

## 7. 最终判定

| 判定项 | 结果 |
| --- | --- |
| 是否覆盖架构核心组件 | 是 |
| 是否违背架构原则 | 未发现 |
| 是否形成代码可实现的接口和 Schema | 是 |
| 是否明确事务和幂等边界 | 是 |
| 是否明确审批安全闭环 | 是 |
| 是否包含可执行测试与验收项 | 是 |
| 是否明确 SQLite 单写者和恢复边界 | 是 |
| 是否明确 Codex SDK 集成和质量门 | 是 |
| 是否已有代码实现 | 否 |
| 是否可宣称代码符合架构 | 否，待实现后补检 |

**最终结论：实现设计通过架构一致性检查，可作为编码基线；代码级一致性尚未验证。**
